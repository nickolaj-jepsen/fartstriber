# Architecture

The CLI does every deterministic step and writes files; the agent judges the files and edits design scripts. The brief is `docs/plan.md`; how iRacing behaves, as measured, is in `docs/sim.md`.

## Designs

A design is `designs/<name>/design.py` with a module-level `KIT = "<kit name>"` literal and `build(kit, p) -> Livery`. The script is run in a fresh module on every build, so module state cannot carry over. `KIT` is read from the source without running it, so hashing never executes a design. What the script prints goes to stderr, so it never mixes with a command's output. A design with `ROLE = "fixture"`, also read from the source, checks a kit or the library and is never raced; designs only the tests build live in `tests/fixtures/designs/`.

`p` is the script's `Params` (a frozen dataclass subclassing `livery.params.DesignParams`), or plain `DesignParams`. Each knob is `param(default, lo, hi)` or `param(default, choices=...)`; `--set k=v`, wedge sheets and seed sheets override fields by name, checked against type and range, without editing the script. Randomness comes only from `p.rng("name")`: a numpy generator seeded from `p.seed` and the stream's name, so adding a stream never shifts another.

A `Livery` is a base colour and material plus elements. Each element has an id, a kind, its SVG in template pixels, a material, a z-order, tags, and (for elements placed in car space) where it sits in car space, for the lints.

## Design library

`livery.primitives` draws in car space through the kit (see Kits): side views (u nose 0 to tail 1, v sill 0 to top of the side 1) and the top view (u, w left -1 to right 1). Primitives that cover several views return one element per view, ids suffixed with the view.

- Car-space shapes (`band`, `stripe`, `shape`) are cut to every island they land on. `band` leans by an angle seen on the side and carries on over the top from where it leaves the side. A stretch of edge the near-tangent lint would fail (see Lints) is snapped onto its line or clear of its reach, whichever moves it less, by at most the reach, tapering back into the rest of the edge; the lint's own measure confirms each move, and a stretch no move fixes is left for the lint to name. `lint.json` and `check.json` list every move under `snaps`: element, onto or clear of what, how far, and where.
- `text` and `sponsor` are laid out flat at their anchor with the map's local slope, in a reading frame per view: on the sides left to right as seen (so nose-wards on the right side), on top as seen from the front. They are clipped to the anchor's island. `mirror_sides` places one on both sides; glyphs are laid out afresh, never mirrored. A real logo the owner supplies is placed as a sponsor (below).
- `panel`, `pattern_fill`, `clip_to` and `clip_out` work on regions: a part or group of the kit's body model (Kits), an island id, or a view name (several for the clips); `geom.outline` and `patterns.hazard` without a view, and `patterns.scatter`, take the same names. `kit.part(name)` and `kit.parts()` give the parts, `kit.feature(name)` and `kit.features()` the features in car space (`at`, `box`, `geometry()`), and `marks` takes a feature's name for its anchor. `svg(raw)` is the escape hatch in template pixels.

`livery.geom` is for designs that draw many pieces. It projects car-space shapes in batches into one element per view, through the view's maps or a design's own set of pieces, and rakes and grows them at the view's scale (`carspace.px_per_unit`). It cleans pieces to the output lint's minimum feature and tests them against the near-tangent lint's lines, reach and run (`geom.edges`), read from its thresholds, so a design never copies a lint number. `geom.outline` strokes a shape's edge, or only the split it shares with another field: each keyline or pinline is measured in the texture from the mapped edge, so it is as wide on every island, none runs along a seam the shape crosses, and none is thinner than `min_outline_px`. Each stroke is its own element, tagged `stroke_of:<id>`, and follows its shape's edge where `shape` snaps it.

`livery.typeset` sets type as glyph geometry: each font's outlines through fontTools, kerned as resvg kerns them, projected like shapes, so type crosses seams. `type_block` stacks a designation and small lines on one start edge raked with the design's lean, with one line gap, a shear, outline strokes and a plate padded equally, square to its raked ends. It refuses a glyph the paint would cut (glass, an arch, an unmapped part) and type under `min_text_px`; its glyphs are a `text` element to the lint, and its plate is never snapped, so its padding stays equal.

`livery.patterns` holds the 10 m layer's devices: hazard tape, dissolves (cells in tiers of size, densest at a line and thinning out, coloured by zone, drawn from `p.rng`), dash runs that end a band, stripe bundles, chevron lanes, and pixels scattered over islands no view maps. Their pieces are sized to survive the lint's minimum-feature opening. A designed piece (a hazard region, a band's kept part, a dash, a chevron) is snapped as `shape` is, and one no snap clears is an error naming it; a dissolve leaves out a cell it can't keep clear.

`waive(element, check, reason)` (a tag `allow:<check>`) waives one output-lint check for one element, visibly in the script. The reason is required: `check.json` lists every waiver with its reason and the findings it kept out of the report.

## Sponsors

A brand is a folder of one-colour SVG variants (`wordmark`, `lockup` with the mark beside the wordmark, `mark`), a `brand.toml`, and the `draw.py` that made them with the helpers in `livery.sponsors`. A real logo the owner supplies is a brand too, with `source = "supplied"`, its file kept byte for byte. Builds read only the SVGs; a redraw rewrites them, and a changed variant loses its approval. The roster is `assets/sponsors/`, indexed by `roster.md` (name, category, lettering voice, mark, own colours, what the name check searched and found, and the owner's yes or no); a design's own themed brands live in `designs/<name>/sponsors/`, are looked up first and need no approval. Fireproof is a roster brand (`source = "owned"`), its mark and wordmark kept byte for byte.

`brand.toml` records, per variant, its aspect, ink share, thinnest stroke and narrowest counter (shares of its height, measured as the largest opening that removes no solid piece) and its approval date. A variant's minimum height is `min_stroke_px` over the smaller of the two, in texture px at the spot it is placed; a brand with `large_only = true` (a didone that lives on its hairlines) is never placed below `large_min_px`, so it goes on a roof, bonnet or door, never in a sill row.

- `sponsor` places one brand by `height` or by `fit=(w, h)`, in one colour or `"own"` (the file's colours). It refuses any variant below its minimum height. A roster variant not yet approved is placed and builds; its approval is needed only by the final review and install (Approvals).
- `sponsor_group` spreads brands along a line, as a row or a column, in the order given. Each mark's height goes as (ink × aspect)^-0.25, between equal heights and equal ink, the tallest at `height`; spare length goes into the gaps. A group that doesn't fit shrinks, and fails rather than go below a minimum size; a brand twice in one group fails too.

Race markings, the technical marks a raced car carries (tow, cut-off switch, extinguisher and the like), live in `assets/marks/` as folders of the same kind, unapproved until `livery review --marks` and gated like roster variants. `marks` places one at a car-space anchor; one that points has a variant drawn each way, picked to point at the nose or the tail rather than mirrored.

## Lints

Both run inside `livery check`, which fails on any error, and alone as `livery lint`, which writes `lint.json`.

- The design lint (`lint/source.py`) reads `design.py` without running it: imports only from math, dataclasses, typing, itertools, numpy, shapely and livery; no `random`, `numpy.random`, `time`, `datetime`, `hash`, `id`, `open`, `eval`, `exec` or `__import__`; no mutable module-level state and no `global`. It needs the `KIT` literal and `build`. It runs first, so a failing script is never hashed or run: a syntax error or a missing `KIT` is a check error like any other. It warns where a script edits the SVG text a primitive drew (`.svg.index`, `.svg.replace`) or copies an element through `__dict__`: those break silently when the library changes. It also warns on a literal island id that its kit's body model names as a part, naming the part.
- The output lint (`lint/output.py`) renders each element alone at half resolution and checks it against the kit: off the islands; over a keep-clear zone (an error for text and logos); under a `keep_clear` feature of the body model, which the sim draws over the paint (an error for text and logos, sponsors and race markings included, a warning for other paint); text or logos under an `occluder`, which hides them from some views (a warning, `occluded`); text or logos that read mirrored or backwards on the car, judged through the kit's maps rather than the texture; an element tagged `crosses_seam` that covers one side of a seam pair and not the other; an edge running alongside a line without meeting it (near-tangent, below); transparency, filters, masks and any `<image>`; strokes, features and text below minimum sizes; more colours than the palette allows; a colour under a metal finish brighter than the sim shows under it (`finish_reach`, a warning: the kit's measured reach, `kit spec`); low contrast under the sim's number. Thresholds are in `policy.toml` `[lint]`, their only source: one missing is an error.
- Its camera checks judge what shows of each element once the elements drawn after it are painted over, as the preview views see it, and only warn. `livery.visibility` turns the kit's calibration capture (Kits) round: per texel and view, whether a pixel samples it, its footprint in texels per pixel, and where on screen it lands, so a fold in the body shows where a texel's neighbour jumps off the line through its other neighbour. They warn on text, sponsors and marks no view sees well (hidden, or more foreshortened than `max_texels_per_px` in every view) or that straddle a crease a view sees well; on detail (a pattern, or an element of many separate pieces) mostly where no view sees it well; and on lines and pieces narrower on screen than `min_screen_px` in every view that sees them, naming the views. The tables are cached per capture in the machine state dir. No check hash covers the capture, so a new one changes these warnings without re-checking; on a machine without the kit's capture they are skipped with one note.

Near-tangent (`lint/edges.py`) judges edges against lines where the paint stops on the car: island outlines less the stretches `seams.json` pairs (the paint carries on across them), shut lines, and the outlines of the strict keep-clear zones. An edge is judged only against its own island's lines, because another island's outline a few pixels away in the texture is elsewhere on the car. An edge within `MEET_PX` of any line or outline meets it, so where an element was cut to its island is no edge. A run is the length of line a free edge runs alongside within `near_tangent_px`, measured along the line; one of `near_tangent_run_px` or more fails, naming the line and where.

## Flat preview

`livery preview flat` writes `flat/views.png` (the left side, top and right side, each car-space pixel looked up through the kit's maps, so the design is seen as it sits on the car), `flat/car.png` (the front three-quarter view of the right side that iRacing's UI previews cars with, rendered from the bake in the local install's `httproot` (what it holds: `docs/sim.md`), extracted once into `.cache/ui-preview/`), `flat/squint.png` (small and blurred) and `flat/overlay.png` (the texture under the wireframe, keep-clear zones and shut lines, and the body model's `keep_clear` features and occluders, named). `car.png` has no spec map, number or sim light: it checks how the layout sits on the body, and the critic sees it only when it compares concepts. `livery sheet <design> --wedge k=a..b..step` and `--seeds a..b` tile the views and the car view for each value; `livery sheet a b c` tiles designs, with the side shot of each one's latest sim run of the same build (else of its latest run, labelled an older build).

`preview flat --baked` also writes `baked/` (`baked-sets/<key>/` with `--set`): each preview view as the sim would show the build, rendered from the kit's calibration capture (Kits) without the sim, as `<view>.png` and a `sheet.png` of them cropped to the car, its stamp naming the capture. Each car pixel samples the paint and spec at its texel from box-filtered mips in linear light, filtered as a GPU's anisotropic filter does: at the mip of its footprint's short axis, averaged over as many taps along the long axis as it is times longer, up to 8. Each material the spec puts there is looked up in that material's ladder at that pixel, interpolated between ladder steps in a power curve fitted once per capture to its gloss ladder (output^g linear in grey^k); materials mix by coverage in linear light, over the view's background frame. Car pixels the geometry didn't decode copy their nearest neighbour; the sim's number, which no paint moves, shows from the background frame. `livery sheet --wedge … --baked` and `--seeds … --baked` tile those views for each value (`<sheet>-baked.png`).

A capture bakes only while what its shots depend on holds (a ladder for each of the kit's spec presets, its canvas, the profile's frame and preview views, the replay, the track camera set, the sim's graphics options, the car's model; not the maps, which say where car space lands in the texture, not which texel the sim shows where), and a refusal names what moved; and only once it passed `livery bake check <kit> [design]`. That renders the calibration fixture (and the design) baked, shoots each build with one real `livery preview sim`, and compares them on the decoded car pixels more than 2 px inside the silhouette, at the capture's window size: median and p95 per channel per view, a side by side and an error picture into the capture's `check/<design>/`, and the result into its manifest. It fails if any p95 is over 12 (what it measured: docs/sim.md). `livery bake status` says whether baked views are usable. Bake check takes the sim, so it is the session's step, not a builder's.

Every preview records the build it shows (`livery.stamps`): `flat/build.json`, `baked/build.json` and each sheet's `<sheet>.build.json` hold the build's TGA digests (each tile's, on a sheet), its design and toolchain hashes and the `--set` values, as a sim run's `manifest.json` does. `preview flat --set` writes to `flat-sets/<key>/`, so `flat/` always shows the script as it is. A final review, an approval and a critic pack take only previews whose stamp shows the checked build: a stale `flat/` is rendered again, sim shots can't be.

## Kits

A kit (`kits/<kit>/`) is tool-written; edits go through the `livery kit` commands, run in this order. `kit.yaml` holds what a person reads (canvas, paint folder, the views it maps, bleed, spec presets and their compensation, keep-clear boxes), its version, which each fit raises, and the fingerprint (size and sha256) of the template and the car's model in the UI's `httproot` it was made from; `maps.json` holds the islands and fitted maps; `body.yaml` the body model (`kit label`, below). Four files a build never reads: `profile.toml`, how the sim shows the car (the replay it is framed on, by SubSessionID and, when that isn't the user's preview replay, its track; the frame; the car's size once its cameras were sized for it; each preview view's camera group and pose; the critic's crops), `fit-report.json`, the last fit's report, `review.yaml`, the open questions and map problems the kit review lists, and `approved.json`, the owner's accept with the hash of the kit's other files. Kit capture, fit and review refuse a kit whose car model iRacing has since updated.

`kit add <psd> --car <kit> --paint-folder <folder>` adds a car in one command (`livery.kit_add`): extract, a profile on the open replay if it shows the car (else the user's preview replay) with preview views on camera groups of the kit's own, the preview cameras (with `--arm`, below), `sim pick-frame`, the calibration capture (`kit capture`, below) unless the current one is of the kit as it is, `kit spec`, fit and kit review. Each step is skipped once done, so running it again carries on where it stopped; it stops with the next step wherever the owner is needed (closing or reopening the replay, saving the track's camera set, the review) or a step can't run yet.

A pose the profile lacks is the default for the car's size (`cameras.preview_poses`): the McLaren's cameras, as many times farther out as the car is longer or taller than the McLaren, whichever is more, and raised and aimed with its height, so a car takes the frame the McLaren takes and a longer one never runs off it. The size is the car's paint seen square-on from its side; a kit with none recorded is sized as the McLaren, whose own poses are these defaults.

- `sim pick-frame <kit>` picks the frame on the open replay (`livery.pick_frame`). It seeks across the replay reading the car's telemetry (lap position, track surface, pit road, yaw rate or steering where the sim gives them) and keeps on-track frames where it turns least, spread around the lap. It shoots each candidate from every preview group with the car painted white and then black under a matte spec, so the pixels that differ are the paint whatever lies behind it: a view passes when the car is whole in the frame with a margin, about centred, and shows at least 97% of the paint the clearest candidate shows. The straightest candidate every view passes goes into the profile with the replay's identity, and the critic's crops if it has none. The side views measure the car; when the cameras don't fit it (it runs off, or they would be sized more than a tenth differently), the profile gets cameras sized for it on new groups instead of a frame, and the replay has to be reopened before picking again. `--check` paints nothing: it shoots every preview group at the profile's frame in the policy's order and the reverse, and fails if a view differs by more than half a percent of its pixels.
- `kit extract <psd> --car <kit> --paint-folder <folder>` reads the iRacing template. Islands are the pieces of the template's paintable area inside its green island outlines (`Wire` layer). The outlines are dashed, so they are grown 3 px to close; where an island still leaks into the thin gaps between outlines, its thick part is recovered as an island. Writes `overlays/islands.png` (index per pixel), `overlays/mask.png` (the islands), `regions.svg` (one outline per island), keep-clear zones from the template's number and sponsor blocks (`overlays/keepclear.png`), shut lines (`overlays/shutlines.png`: the wireframe draws panel gaps thicker than mesh lines), and the mirror axis the two side views share. Re-running it on the same template keeps what later commands wrote; another template may number its islands differently, so it drops the maps and the approval.
- `kit fit <kit>` turns the calibration capture (`kit capture`, below) into maps from car space to texture pixels. It reads five of its views: each side square-on, the three-quarter view that sees each side's up-facing strips (front34 the left, rear34 the right) and the top. Every map holds only where it was measured: in the texture, the texels its samples showed (closed over small gaps, holes filled) grown by 8 px; in car space, their car points grown by 0.03, which a design can anchor in at an island's edge. Thresholds are in texture px of a 2048 px template and scale with the canvas. The stages:
  - Side frames: a side view's screen axes are the car's, so u runs nose 0 to tail 1 along its x and v sill 0 to top of the side 1 up it, framed on the side panels (islands of a side band with a mirror partner; the bands also hold parts one camera sees and the other doesn't). The side that decodes more of its panels is framed by their extent; the other by matching it texel for mirrored texel, so a bank that hides one side's sill doesn't move its frame, and a design at one (u, v) lands on mirrored texels of both sides.
  - Side maps: a panel its side sees on enough pixels gets a quadratic from (u, v) to (x, y) (affine where a quadratic would fold), plus a residual grid: the quadratic's median miss per small car-space cell, smoothed, looked up bilinearly; a large island bends more than a quadratic follows, and the miss piles up at its edges, where the next island meets it across a seam. Texels its own side didn't see (under the bank) take its partner's samples, reflected. Small islands get an affine map from their side's samples and the three-quarter view's, carried into (u, v) tile by tile through a quadratic on the texture cells both saw around the tile: that is how strips on the fender and door tops, edge-on from the side, are mapped. That includes the fender-top strips the template files with the top view, found where the top shot puts them far from the top model's w.
  - Mirror: an island neither side mapped takes its partner's map reflected about the mirror axis. Partners both sides mapped should agree on a symmetric car (the report's `sides_agree`); where they don't, the side that saw its island twice as much keeps its map, else the map whose reflection misses the other side's samples by less, and the other is replaced by its reflection.
  - Top: w (left -1 to right 1) is linear in texture y about the mirror axis on the top islands. u comes from the top shot's screen, an affine map fitted on the texture cells it shares with the side panels, where a shape crosses from a side onto the top. Each top island seen enough gets a map (u, w) -> (x, y) with a residual grid, from the top shot, or from the side shots (u from their frames) where it hardly sees the island; an island across the centre line fills the half no view saw from the other half, reflected. The parts of side islands the side maps don't hold that face the top camera (fender and haunch tops, door shoulders, the wing) get a map too, with w where the large top islands put that place in the top shot (a quadratic of its screen); where a top island curves down its texture's w strays from that (docs/sim.md, Fitting from the preview views), and a shape crossing from there onto the side island's top can jog. Each texture pixel has one view: the side map keeps what it holds. The other top islands use one linear u scale, only on the texels some view saw.
  - Seams: `seams.json` pairs texture points on two islands that are the same spot on the car. Each island edge is mapped to car space and back through every other island of the view; a pair is kept when the second island's inverse returns to the same car point, to 0.01 of a 2048 px template (more on a smaller one), from both a nearby start and the middle of its measured area, which rejects folded maps.
  - The report gives each island's samples, rms over the samples the robust fit kept, and p90 and dropped share over all of them. `--compare` writes nothing: per island and view, the new map's p90 and the current one's on the same samples (in the car space that fits the current maps best: two fits frame the car a little differently), how far paint at the same car point moves (p90 and most), the two fits' `sides_agree`, and the share of each approved design's car pixels that would move. `--keep <ids>` keeps the current maps of those islands.
- A fit writes `maps.json`, `seams.json` and `fit-report.json` (its report and the compare with the maps it replaced), raises the version and clears the approval: new maps go back to the owner. Any other change to the kit's build inputs voids it too. A final review and `livery install` refuse a design on a kit that isn't approved as it is.
- `kit label <kit> <parts.json> <features.json>` writes the body model, `body.yaml`, from a labelling pass (the kit-calibrate skill); its input is the file's own sections as JSON, plus `questions` and `fit_problems`, which go to `review.yaml`.
  - A part is paint by name: whole islands, an island cut by a car-space polygon on one view (`cut`: the door and the haunch share one island, split at the shut line), or the rest of its islands once the other parts' cuts are out (`rest`). A group paints parts together (`front_panel_l`). An island no part names can be noted under `unnamed`.
  - A feature is car-space geometry on one view (a point, line, box, polygon or several boxes) of a kind: `keep_clear` (the sim draws it over the paint: the door light panel), `occluder` (it hides the paint under it from some views: the carbon side blade), `opening`, `unseen` (paint the square-on shot never sees), `zone` (a template box in car space), `line` (arches, shut lines, creases) or `place`. `same_as` gives one another name.
  - Each part and feature says how sure the labelling was (`sure`, `likely`, `unsure`) and why. The command refuses an island the kit lacks, overlapping cuts, a rest no cut leaves, and a feature none of whose samples land on its view's mapped paint, and reports how much of each feature does. A changed body clears the approval, as a fit does.
- `kit review <kit>` writes a labelled overlay (islands by view), the parts and features by name on the texture (`parts.png`) and on the car views (`body.png`), unsure names marked, and shoots the calibration livery (`livery.calibration`: bands at fixed car-space positions, drawn through this kit's maps) on the kit's car, in the preview shots, into `.cache/kit-review/<kit>/`. Its review item lists the unsure names, the open questions and the map problems for the next fit. The `calibration` fixture design is that livery on the McLaren, so a library change that moves it shows in `build --all`.

`kit capture <kit>` is a car's calibration capture, shot at its profile's preview views: Gray-code geometry under a matte spec and a grey ladder (seven steps, 0 to 255) under each spec preset. The geometry (`livery.graycode`) codes all 11 bits of a texel's u and v in 8 patterns, each shot with its inverse: each pattern holds one bit that flips inside the compressed blocks of the mips the views sample and coarse bits that don't (docs/sim.md, Rendering). A white and a black probe give the car's pixels and each bit's confidence. Bits are read coarse to fine, allowing one unsure bit (a pixel on a code boundary sits at the boundary), and a plane fit over the neighbours on the same panel gives each pixel's texel to a fraction of one and its footprint in texels per pixel. Each paint is a sim run of its own, so other runs queue between paints; `--resume` carries a stopped capture on after its last finished paint, and refuses one shot with other views, frame, replay, track camera set, graphics options, car model or kit, or another window size. Per view it keeps, for each car pixel, the uv, footprint, finest bit and confidence (`geometry.npz`) and what each ladder step shows (`ladder.npz`); the manifest holds what the shots depend on and a summary (share decoded, plane-fit agreement, each material's response and white clipping, the grey a finish needs to show what gloss shows, how far it reads from gloss). The frames are deleted unless `--keep-frames`, and `current` in `kit-capture/<kit>/` in the machine state dir, shared by every worktree, points at the last whole run, which baked previews render from (Flat preview).

`kit spec <kit>` writes the finishes' compensation into `kit.yaml` from the capture's ladders (`livery.kit_spec`): for each preset with metal in it, which the sim renders darker, the paint value per colour channel that shows each ladder grey as gloss shows it (the median output over each view's pixels, then over the views), and the brightest grey it can show at all. `--preset m=R,G,B` sets a preset first and shoots its ladder again into the current capture, beside the capture's own (`calibrate.reshoot`), so a checkout still on the old preset keeps reading the old ladder; a capture bakes while it holds a ladder for every preset as the kit has it.

`livery.carspace` draws car-space polygons through these maps: a shape is mapped onto every island of its view and cut to that island's measured area with shapely, so the SVG carries only visible pieces and no clip paths.

## Build

1. Compile: elements in z-order (ties keep insertion order), one `<g data-id data-kind data-material>` each, above a `base` group.
2. Spec SVG: the same document with every fill, stroke and gradient stop of each group replaced by its material's spec colour, and `<image>` replaced by a rectangle in that colour. Clip paths and masks are left alone because they define coverage, not colour. Spec colours are `(metallic, roughness, clearcoat)` in R, G, B, per the template's spec group.
3. Render both with resvg, loading fonts only from `assets/fonts` (system fonts are skipped), so text renders the same on any machine.
4. Bleed: pixels outside the islands, up to the kit's bleed width (16 px), and each island's 2 px rim take the colour of the nearest pixel inside that rim, in both paint and spec. The rim is antialiased against the base colour, so copying it outward would draw a light hairline along every seam. Mipmapping then blends paint with paint at island edges, never with the background; without it, seams show as thin lines of whatever lies between islands.
5. Compensation: the sim renders paint under a metal finish darker (`docs/sim.md`, Rendering), so paint under one takes the kit's lookup for the nearest such preset (`kit spec`), mixed in linear light by the spec's metal channel. Above what the finish can show, it gets white.
6. Write uncompressed 24-bit TGAs, because 32-bit with alpha can render black.

Outputs go to `.cache/designs/<name>/`: `layers.svg`, `spec.svg`, `paint.png`, `spec.png`, `car.tga`, `car_spec.tga`, `check.json`. Nothing there is committed; a build is reproduced from its script.

## Settings

Two files, read through `livery.config` into typed objects; a missing key is a `ConfigError` that names it. `policy.toml` in the checkout is the project's policy, the same in every checkout: the lint thresholds and the views a preview shoots. The user's own settings are `config.toml` in the state dir (The sim), shared by every worktree: the owner's name (which messages, help texts, approvals and the critic's pack use; 'the owner' without it), customer and team IDs, the archive folder, the iRacing documents and install folders, the sim's process, and the preview replay (file, sha256, SubSessionID, track name and camera.ini path). `livery.example.toml` documents every key and `livery config show` prints them; a first run without the file writes it from a checkout's old `livery.toml`. How the sim shows a car belongs to its kit (Kits). Tests use settings of their own, never the user's.

## Gates and determinism

`livery check` builds the design twice in one process and once in a fresh interpreter with a different `PYTHONHASHSEED`, and fails on any byte difference between the outputs. An in-process repeat cannot catch set or dict iteration that follows the hash seed; the fresh process does. It writes `check.json` with the result, the output digests and three hashes, each of what a build reads and nothing else:

- Design hash: the script, its kit's files but `profile.toml` and `approved.json`, and what a build can load from `assets/` and the design's own `sponsors/`: font files, variant SVGs and `brand.toml` less its approval dates (not `draw.py`, `roster.md` or licences). Approving a kit or a brand sends no design back through check.
- Toolchain hash: the livery modules a build can import (the import closure of `check` and the design library, read from the source) with comments and docstrings stripped, the versions of the runtime dependencies (resvg-py is pinned exactly), and the Python version. Editing the CLI, the critic or the sim code, or rewording a comment, does not force a re-check; changing build code does.
- Policy hash: `policy.toml`'s `[lint]`, which the lints and the library's minimum sizes read, so a tightened threshold re-checks every design.

`livery build` writes outputs only after a passed check. It reuses a stored `check.json` that passed with all three current hashes instead of checking again; otherwise it runs check, and writes no build output if check fails. Sim preview and install refuse a build whose `check.json` does not match.

Errors that say what to do next (an unknown design, a bad `--set`, an unchecked or unapproved build, a sim that isn't ready) are `livery.errors.LiveryError`s: the CLI prints the message and exits 1, or 2 for a bad argument. Any other exception is a bug and keeps its traceback.

Line ends are LF everywhere (`.gitattributes`, and every file the library writes), and text is hashed with CRLF read as LF, so a checkout or editor that adds CRLF doesn't change a hash.

## The sim

`livery.iracing` talks to iRacing only through SDK reads and broadcasts (seek, play speed, camera, the camera state's UI flag, texture reload); `livery.capture` reads the sim's window and grabs it with Windows Graphics Capture. Neither sends input or focuses, raises or restores the window. A preview shoots the views `policy.toml` `[preview]` lists, each at the replay frame and camera group the design's kit's profile gives it. The groups are car-locked cameras that `livery preview cameras <kit>` adds to the camera set of the track the kit's replay is at (`Documents\iRacing\cameras\tracks\<track>\track.cam`; format in `livery/cameras.py`), together with every other kit's on that track, each in a group of its own beside the stock cameras, so no car camera is given up, posed as the profile says (a pose it lacks is the default for the car's size, see Kits): for a car the McLaren's size each side square-on from 25 m, the top from 5° off vertical (straight down, the car would turn with its heading), a low front three-quarter and a high rear three-quarter. A kit `kit add` made names its groups by kit, view and pose, so the group list shows whether the sim has read the set with its current poses. They sit in the car's frame and aim at it, so a view frames the car the same way whichever view came before; the frame is on a straight with a clear line from every camera (`sim pick-frame`). Frames, not session times, because a session-time search lands a few frames off depending on where the replay was. The track's set exists once the owner has saved it from the sim's camera tool, after which the sim points `camera.ini` at it itself. The command keeps that stock set beside it as `track.cam.stock`, `--restore` puts it back, and it changes `camera.ini` only while the sim is closed (the sim rewrites it on exit): it refuses while the sim runs, or with `--arm` waits until the owner closes it and writes then, so one close and reopen loads the cameras. The sim reads the set when a session opens.

Every sim run (preview, kit capture, kit spec's reshoot, kit review, sim pick-frame, and `livery install` with its `--restore` and `--finish`) is a `livery.simsession.SimSession`:

- It holds the sim lock throughout: a named mutex (`Local\fartstriber-sim`), so sessions in any worktree queue for the one sim. The kernel frees it when its holder dies; a file in the state dir names the holder.
- It puts back the paint of a run that died (see Paint folder), then waits, saying once what it needs, until the sim is on the kit's replay (the user's `[replay]` `subsession` and `track_name`, as the SDK names them, or the replay the kit's profile names; any replay for `pick-frame`) with the kit's car, the camera groups the run shoots and its window open, and behind other windows: a run never drives the sim while the owner has it in front. `install` uses the sim only if a session with the car is open and behind other windows, and otherwise leaves the reload to the sim's next load.
- It notes the camera, the UI flag, and the replay's frame and speed. Before every broadcast and every frame it checks that the sim is still behind other windows and not minimised, and stops once it isn't. One capture session serves the run, cropped to the window's client area.
- A reload goes old paint, plain grey, new paint; `reload` frames the run's first shot and waits for the steps and a steady frame. Without a grey step it counts once the frame changed, or when the new paint is near grey or the same as before, and fails otherwise.
- Leaving, on errors too, it puts the paint files back, reloads so the sim shows them, and puts the camera, UI and replay back as they were; with the sim in front it leaves the sim alone and says so. It writes the run's `manifest.json` (presets, window size, reloads, timings, failure, and the build's digests or the kit's hash) into the run's folder.

Machine state lives in `%LOCALAPPDATA%\fartstriber` (or wherever `FARTSTRIBER_STATE` points), shared by every worktree of every checkout: the user's settings, the lock's holder, the paint journal, the install backups, the shot references, the review queue (see Review) and the telemetry (see Records). `livery sim status` reports, without sending the sim anything, what the next run would find: the replay file against its sha256, the open replay against the settings, the car and its paint names, its kit's preview camera groups, the lock's holder, journals of dead runs, whether Trading Paints Downloader runs, and the window.

`livery preview sim` refuses a build unless its `check.json` passed with the current design and toolchain hashes and the TGAs on disk are the ones it checked; it reads them once, before waiting for the sim. It installs the build under the session's paint name, reloads, and shoots every preset into `sim-partial/<time>/`, which becomes `sim/<time>/` once every shot is taken, so `sim/` holds only whole runs. A shot whose replay-UI bands (the session bar along the top, the controls along the bottom) differ from the same view's clean shot has the UI over the car, which the sim draws while the cursor is over its window: it is taken again once after a short wait, then refused. The clean shot is kept in the state dir per replay, frame, camera group, window size and track camera set; a view's first shot counts as clean unless the cursor is over the sim window.

## Review

Every decision the owner makes goes through `livery review`: one localhost page (standard-library HTTP) for every session on the machine, showing one item at a time. Each `livery review` queues its items as a group in the state dir (`review/<id>/`: its checkout, branch, process and items; the decisions; what Apply wrote) and blocks until the owner presses Apply on that group. Whichever waiting review holds port 8765 serves the page from the queue; when it exits, the next one takes the port over and the page, which polls, carries on, so no server outlives the reviews. The page groups items by session and serves a group's pictures only from inside its checkout. A checkout has one waiting review at a time, since two Applies there would commit over each other. A group whose process died is stale: the page keeps taking decisions on it, and the next review from that checkout takes them over for the items still in it, so a review can stop and resume. `livery review --list` lists the groups; `--cancel` takes this checkout's (or the named ones) off the page, and a review waiting on one exits. Items are designs (several are concepts they can pick or mix, one is a final), a kit (`--kit`), proposed brands in `roster.md` (`--roster`), drawn brands with a variant not yet approved (`--sponsors`: a sheet per brand, each variant dark on light and light on dark, large and at sill size, then the `sponsor-roster` design if it exists), `references.md` rows (`--references`), race markings not yet approved (`--marks`) and the edits a retro proposes (`--proposals <file>`: a JSON list of `{title, body}`). Keys: A accept, E edit, R reject, S skip, M mix, on designs P park and 1–4 to rate, and on references, roster rows and drawn brands Shift+A accepts every one of that review still undecided. Edit and mix say what to change, so the server refuses them without a note; the page saves the note as it is typed. A design shows its sim shots in `policy.toml`'s view order, then its flat views, the iRacing UI's car and the squint. Accepting a design means good enough to race; park stops iterating without approving it, so nothing is pinned or installable. The rating (1 done with it, 2 fine, 3 would race, 4 love it) is optional and stored with the decision.

Apply runs in the process that queued the group, in its own checkout, so its commit lands on that checkout's branch. It writes what review owns (a kit's `approved.json`, if the kit is still as shown, the yes/no column of `references.md` and `roster.md`, a brand's or a race marking's approval, or removing a rejected brand; brands and markings first, so a final that places one they accept in the same review can be pinned), then appends every decision to `prefs/decisions.jsonl`, the committed decision record: their note verbatim, mix, rating, time and review id, and for a design the sim runs its item showed, the design hash they decided on and the critic's latest verdict on that same hash. Then, in a git checkout, it commits exactly what it wrote plus each decided design's folder (and a sponsor's brand folder, or the markings' folder), with their notes in the message, and never pushes; it skips the commit when a file it wrote already had changes it didn't make. It prints every decision as JSON, with the accepted and edited proposals for the agent to make; the agent writes `prefs/log.md` from it in the owner's words, its own context lines starting `Context:`.

A design's item opens with the owner's last decision on it in the ledger: the date, the decision and the note verbatim; their latest note too, when that decision had none; the critic's latest judgement of that note (Critic); and, while the sim run they saw then is still in `.cache`, `diff/reviewed-vs-now.png`: that run beside the one shown now, a view per row. The critic's scores and call never reach the page: the ledger sets them beside the owner's decision to measure agreement, and showing them would anchor it.

## Approvals

A final review shows the checked build on disk and only opens for one: its flat preview, rendered again unless its stamp shows that build, and the latest sim run of that build, or the latest run marked as of another build when none is. Accepting it writes `designs/<name>/approved.json`: the build's output digests, its design, toolchain and policy hashes, the design hash's parts (script, kit, assets, the design's own sponsors), the build's waivers and the roster sponsor variants and race markings it places (from `check.json`). It also keeps that build's paint, spec and flat pictures in `.cache/approved/<name>/<digest>/`. Nothing is pinned if the build changed while the review was open, if `flat/` no longer shows it, or if it places a roster variant or race marking the owner hasn't approved; the item and Apply's output name them. `livery install` installs only the approved build, and only while what it places is approved (`--unapproved` overrides, and says so).

A kit refit or a library change moves every design's pixels without touching its script. `livery build --all` builds every design and reports each as approved (the installed TGAs are the pinned ones), changed, unapproved or failed. Fixtures are listed apart, and one without an approval is built, never unapproved. It exits 1 when a design failed or an approved one changed. A design placing an unapproved roster variant or race marking lists it. A changed design lists what moved (those parts, toolchain, policy) and the share of the car's paint and spec pixels that moved by more than a few units (`approvals.TOLERANCE`), and writes `diff/approved-vs-now.png` (approved, now, changed in magenta). A final review of a changed design shows that picture. If `.cache` lost the approved pictures, only the digests are compared.

## Critic

A fresh `livery-critic` subagent (`.claude/agents/livery-critic.md`: the Read tool only, its model pinned, no CLAUDE.md) judges each pack. A judge compares far more reliably than it scores, and favours whichever of two images comes first, so most of its jobs are comparisons run in both orders.

`livery critic pack` makes a folder of what the critic may see, never the design script, with a manifest that points only inside it and names the owner whose taste it judges. Every pack holds copies of the rubric and the taste table (`.claude/skills/livery-design/rubric.md` and `taste.md`, which designers read too), `references.md` and `prefs/log.md`, and per design `kit.md`: what the sim draws over its car and what hides its paint, from the body model.

- A round: the shots of the latest sim run of the checked build, each with a distance image (shrunk to 200 px, then enlarged three times, because Claude misreads images under 200 px); close crops across the beltline and nose (boxes in the kit's profile); the squint of that build; the brief; the pictures of the reference rows the brief names (`References: 25, 32`) and the boring anchors, both cached by `livery references fetch` in `.cache/references/`; the design's earlier verdicts with the builder's answers; and the owner's latest note on it (the latest ledger line on the design with a note, until they accept the final). It refuses a design without a current check, sim runs of any other build or that recorded none (`run livery preview sim`), and a round whose last verdict's fixes aren't answered. `--adversary` packs the same without the history or the note, for a second critic told to find the most boring part of the car.
- `--baked`, with a round, `--compare` or `--adversary`: baked renders of the checked build (Flat preview) in place of sim shots, for the autonomous middle rounds. They go into `baked-runs/<time>/`, which, like a sim run, is never written over, and the manifest and the verdict record say `baked`.
- `--compare`: this round's shots and the last round's, as A and B in one pack and as B and A in another; nothing in either says which is newer.
- `--pairs c1 c2 …`: one pack per ordered pair of concepts (briefs, flat views, `car.png`, squints), named `A__B`. Concepts may be unchecked, so their flat previews must be of the scripts as they stand.
- Several designs and no flag: the legacy concept ranking on sim shots.

The design's `verdicts.jsonl` is the one verdict store. Each record carries what the pack showed, remembered in the build folder (`critic.json`) until it is recorded: the design hash, the shots, a hash of the rubric, taste table and critic prompt, and the pinned model.

- `critic record`: a round, numbered. Each fix of the last round, and the owner's note when the pack carried one, is resolved, partly or not, naming the pack image that shows it; every taste row passes or fails; rubric scores and a 1–10 overall are logged only; at most three fixes, each optional or not; the critic's call, iterate or rework; `lint_missed` and `blocked`. Records from before v2 have no `version` and are still read; their fixes count as optional only under a ship verdict. Those written before `verdicts.jsonl` existed are marked `backfilled` (from the old notes and metrics); their shots are `inferred` from the packs' times and their design hash is unknown.
- `critic compare <design> <first> <second>`: the answers to the two compare packs, in the order printed: better or worse where both orders agree, else same.
- `critic adversary`: up to three findings, the most boring first, each optional or not.
- `critic rank --pairs <dir>` fits Bradley-Terry to the pair answers (`A__B.json`); `--verdict` takes a legacy ranking. The ranking goes to each concept's `verdicts.jsonl` with its place; review and `livery stats` set it beside the owner's pick.
- `critic answer` stores the builder's reply to each fix (done, blocked or skipped, with a note) and prints the blocked ones.

`livery critic status` computes ship: the last round was judged on sim shots, not baked renders, so the round that ships and every review see the sim; it leaves no open fix that isn't optional (its own, or one of the round before that it marked partly or not), nothing blocked and every taste row passing; it judged the owner's latest note resolved; a compare with the round before isn't worse; the adversary's top finding on the same shots is optional; and the design hasn't changed since. Otherwise the critic's call stands. Two compares in a row that come out the same are reported as a plateau.

## Records

Outcomes are committed: the verdicts (Critic), the decisions (Review) and the approvals. A design's `brief.md` and `notes.md` hold only where it stands now; how it got there is in its verdicts and in git.

Telemetry is this machine's alone, in the state dir (`telemetry.jsonl`, `livery.metrics`). Each `livery` command is one event, however it ends: the command and its arguments, the design and its kit, the design and toolchain hashes when the command knew them, the Claude session id from the environment, ok, failed (a non-zero exit, like a check that didn't pass) or error with its class, and stage durations. A sim run, an install and each review decision also log a line, carrying the run id of the command they ran in. The history from before, a checkout's `runs/metrics.jsonl`, is copied in the first time a checkout that still has it runs a command, each line once.

`livery status [design]` builds nothing: per design, whether its check is current or which hash moved since, whether the TGAs on disk are the checked ones, its approval and its kit's, whether `flat/` and the sim runs show the checked build, and the critic's last round with its open fixes. `livery stats` reads the records and the telemetry: sim runs, failed sim attempts and rounds per design; the critic's rank of each concept the owner picked, and each final decision beside the critic's call on the same design hash (else on the last round before it) with its rating; `lint_missed` by kind; seconds per command and per sim stage, minutes from sim shots to their verdict, and waits for the sim lock. Every command that prints a result takes `--json`, which prints it as one JSON object and sends progress to stderr.

## Design sessions

The owner decides twice, at the concept pick and at the final (the procedure is the `livery-iterate` skill). In between, two saved workflows in `.claude/workflows/` run the agents, and each stops before `livery review`, because a workflow takes no input mid-run. `livery-concepts` has one agent write a concept brief per name, each from a different source, a builder sketch each, a critic judge every pair in both orders, and the top three built and shot in the sim. `livery-refine` runs rounds of a fresh builder, the sim and fresh critics until `critic status` ships the design, or its budget, a blocked fix or a plateau stops it. Once the kit's capture passed bake check, its middle rounds are built and judged on baked renders without the sim; the budget's last round, and the round after a baked one that only its being baked kept from the adversary check, are judged on sim shots. A plateau or a rework call forks three variants once, as sibling designs ranked pairwise against the design; a winning variant is adopted into it. A workflow script has no shell, so the CLI steps between agents (packs, records, status) run in small agents of their own.

A `livery-builder` (`.claude/agents/livery-builder.md`) owns the design named on its prompt's first line (`design: <name>`) and starts fresh every round, its folder being its memory. Its hooks (`.claude/hooks/builder_scope.py`) read that line from its transcript and refuse an Edit or Write outside `designs/<name>/` and the scratchpad, and a shell command that writes files other than through the livery CLI, `uv run` and git, or that runs the session's or the critic's steps. A script it runs can still write anywhere, so when it stops it is sent back once if a file outside `designs/` changed after its first edit or command.

## Paint folder

`livery.paintfolder` has two modes. Sim runs write through `temporary`: before a file (or a spec's `.mip`) is first written, the original goes into a journal in the state dir (`paint-journal/<run>/`, on disk before the write), and the run's end puts every file back and drops the journal. A run that dies leaves its journal, and the next sim run replays every journal whose process is gone (its pid and start time) before it touches the folder. `livery install` writes the final paint under both names (`car_<customerID>` and `car_team_<TeamID>`, from the user's settings) after backing up whatever was there before the first install, in the state dir (a backup left in a checkout's `.cache/paint-backup` moves there on first use); `livery install --restore` puts that back. It warns while Trading Paints Downloader runs. After installing, it reloads so the sim builds the spec `.mip`, archives the `.mip` to `archive_dir`, and takes the spec TGA out of the folder (otherwise the sim rebuilds the `.mip` every launch). The sim only builds the `.mip` for the name the loaded session uses; the other name's spec TGA stays until `livery install <design> --finish` after a session of that kind. Other drivers see a paint only through Trading Paints, which takes the spec only as a `.mip`: `livery export <design>` copies the approved build's TGAs, and the `.mip` archived since its approval, under the upload names (`car_<customerID>.tga`, `car_spec_<customerID>.mip`) into `~/Documents/Fartstriber/export/<design>/`.

## Paint files in the sim

The sim reads `Documents\iRacing\paint\<paint folder>\car_<customerID>.tga` in single-driver sessions and `car_team_<TeamID>.tga` in team sessions, with matching `car_spec_…` files; it writes a `.mip` next to a new spec TGA on reload. Which name applies comes from the session's `TeamID`. A reload passes through a plain grey car before the new paint shows.
